# ADR-0005 — Хранение пользовательских сессий MoodDiary

- **Статус:** принято для учебной среды
- **Дата:** 2026-11-18
- **Контекст:** ЛР6, переход с одного EC2 на Application Load Balancer и Auto Scaling
- **Регион:** `eu-central-1` (Frankfurt)

## Контекст

PHP-приложение MoodDiary использует `$_SESSION` для авторизации и сопутствующих данных (в частности, CSRF). При одном EC2 стандартное файловое хранилище PHP работает, но после создания ALB с несколькими EC2 запросы одного пользователя могут попадать на разные серверы. Когда Auto Scaling завершает экземпляр, локальные файлы этого сервера становятся недоступны.

При этом пользовательские записи уже находятся в **RDS for PostgreSQL**, вложения — в **S3**. Для горизонтального масштабирования требуется общее хранилище сессий, которое не зависит от конкретного EC2 и не вынуждает балансировщик закреплять пользователя за одной целью.

## Рассмотренные варианты

| Решение | Преимущества | Недостатки |
|---|---|---|
| **Файлы PHP + Sticky sessions ALB** | Почти не требует изменения приложения; просто настроить | Сессия теряется при отказе/завершении EC2; пользователь привязан к серверу; труднее перераспределять нагрузку |
| **Таблица сессий в RDS PostgreSQL** | Уже используемая СУБД; SQL и транзакции; общий доступ для EC2 | Увеличивает нагрузку на RDS; дополнительная схема, обработчик и очистка; единая точка отказа Single-AZ |
| **DynamoDB On-demand** | Общее управляемое хранилище, AWS SDK для PHP, автоматическое масштабирование, TTL, не зависит от диска EC2 | Сетевые запросы и стоимость операций; нужны IAM права; TTL срабатывает асинхронно; конкурентные записи требуют внимания |

## Принятое решение

Выбрана **Amazon DynamoDB** для хранения PHP-сессий приложения MoodDiary:

- Таблица `mood-diary-dev-sessions`, режим **On-demand**;
- Partition key `id` (тип String), TTL attribute `expires`;
- Интеграция через `Aws\DynamoDb\SessionHandler::fromClient()`;
- Регистрация обработчика **до** вызова `session_start()`;
- Параметры подключения берутся из `.env`: `DYNAMODB_SESSIONS_TABLE`, `AWS_REGION`;
- При пустом имени таблицы используются стандартные файловые PHP-сессии для локальной разработки;
- IAM policy `mood-diary-dev-app-sessions`: только `GetItem`, `PutItem`, `UpdateItem`, `DeleteItem` для таблицы;
- Политика прикреплена к EC2 instance profile через роль `timecapsule-dev-app-role`;
- Статические AWS access keys в приложении не сохраняются;
- В настройках обработчика используется `hash_key = id`, `session_lifetime_attribute = expires`, `locking = false`.

Код размещён в файлах `src/Core/SessionStorage.php` и `public/index.php` ветки `feat/cloud-lab6-dynamodb-sessions`.

## Последствия и риски

### Положительные

1. Все серверы за ALB используют единое состояние авторизации, независимо от Availability Zone.
2. Отказ, обновление или завершение EC2 не требует повторной авторизации из-за потери локальных файлов сессии.
3. ASG может увеличивать и уменьшать количество серверов без привязки пользовательских cookie к отдельному EC2.
4. TTL позволяет автоматически очищать устаревшие сессии без отдельного cron на серверах.

### Ограничения

1. **TTL в DynamoDB асинхронный:** истёкшая запись может сохраняться некоторое время после `expires`; срок действия необходимо корректно учитывать в приложении.
2. **`locking = false`:** параллельная запись одной и той же сессии из нескольких запросов может приводить к конфликтам. Для производственной нагрузки требуется отдельно проверить стратегию блокировок.
3. Сессии DynamoDB не устраняют зависимость от **RDS Single-AZ**. Если база недоступна, большинство страниц и `/health.php` перестанут работать, хотя хранилище сессий продолжит отвечать.
4. Учебный ALB использует HTTP: для production необходим TLS/HTTPS и безопасные атрибуты cookie (`Secure`, `HttpOnly`, `SameSite`).
5. AMI содержит серверную конфигурацию `.env`. Необходимо ограничивать доступ к AMI и защищать содержащиеся в образе секреты; предпочтительно вынести секреты в AWS Secrets Manager / SSM Parameter Store.
6. DynamoDB тарифицирует запросы и хранение, поэтому требуется мониторинг расходов даже после отключения EC2.

## Подтверждение правильности решения

- Сессия отображалась в DynamoDB Explore table items (скриншот ЛР6 `003-php-session-record-added-to-dynamodb-table.png`).
- После развёртывания AMI v2 и успешного Instance Refresh значение `Served by` менялось между серверами при сохранении авторизации.
- Зафиксированы увеличение ASG **2 → 3** и уменьшение **3 → 2** без потери входа.
- Первоначальные две цели ALB имели статус `Healthy`, а оба экземпляра — `InService`.

## Альтернативы для будущей эксплуатации

Для упрощённой одиночной инфраструктуры можно оставить файловые PHP-сессии. Для нескольких серверов допустимо хранить сессии в SQL-таблице, если производительности БД достаточно и её отказоустойчивость отвечает требованиям. Выбранная DynamoDB лучше соответствует текущей модели горизонтального масштабирования MoodDiary, но должна дополняться мониторингом, защищённым HTTPS-доступом и устойчивой базой бизнес-данных.
