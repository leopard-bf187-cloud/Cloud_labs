## 1. Цель и фактический результат

**Цель:** освоить управляемую базу данных Amazon RDS for PostgreSQL, изолированный сетевой доступ, перенос данных из PostgreSQL на EC2, управление правами и автоматическую остановку экземпляра для ограничения расходов.

Вместо примера `TimeCapsule` использовано собственное PHP-приложение **MoodDiary** — дневник настроения. Оно работает на EC2 с Nginx и PHP-FPM; вложения хранятся в S3, а PostgreSQL содержит пользователей, записи, справочник настроений и метаданные вложений.

**Фактический результат:** в приватной сети создан Amazon RDS PostgreSQL; база `mood_diary` перенесена со старого EC2 `db-server` в новую `mooddiary`; данные совпали по количеству строк; Route 53 переведён на CNAME RDS; соединение PHP с новой БД и работа MoodDiary подтверждены. Созданы IAM-политика, роль и расписание EventBridge Scheduler. Старый `db-server` остановлен на время проверки.

**Граница выполненной работы:** отдельная учебная БД `lab5-db`, Read Replica, восстановление Point-in-Time, тестовая остановка Scheduler, перезагрузка/остановка самой RDS с наблюдением `/health` и CloudTrail **не выполнялись**. Эти пункты не выдаются за выполненные. Остановка старого EC2 `db-server` не является тестом остановки RDS.

## 3. Подготовка сети и RDS (задания 1–3, 6)

Использована VPC из ЛР3. Первоначальная попытка создания DB Subnet Group завершилась ошибкой:

```text
The DB subnet group doesn't meet Availability Zone (AZ) coverage requirement.
Current AZ coverage: eu-central-1b.
Add subnets to cover at least 2 AZs.
```

Причина — обе старые private-подсети находились в одной AZ. Добавлена новая подсеть в `eu-central-1a`, после чего группа `mooddiary-dev-db-subnets` была создана успешно.

![Создание DB Subnet Group](images/001-rds-created.png)

Для базы создана Security Group `mooddiary-dev-rds-sg`: входящий PostgreSQL/TCP 5432 разрешён только от группы сервера приложения, а публичный доступ к RDS отключён.

![Созданная группа безопасности RDS](images/002-rds-sg-created.png)

В Amazon RDS развёрнут экземпляр `mooddiary-dev-rds` с PostgreSQL 16, Single-AZ, классом `db.t4g.micro` и хранилищем `gp3` на 20 GiB.

При создании AWS отклонил срок хранения автоматических резервных копий 7 дней:

```text
The specified backup retention period exceeds the maximum available
to free tier customers.
```

После уменьшения retention до **1 дня** экземпляр успешно создан и перешёл в состояние `Available`.

![База RDS в состоянии Available](images/003-db-created.png)

## 4. IAM и EventBridge Scheduler (задание 7)

Для автоматической остановки RDS созданы:

- **IAM policy** `mooddiary-dev-rds-stop`: право `rds:StopDBInstance` только для `mooddiary-dev-rds`;
- **IAM role** `mooddiary-dev-scheduler-role` с доверенной службой `scheduler.amazonaws.com`;
- **EventBridge Scheduler** `mooddiary-dev-rds-nightly-stop`, состояние `Enabled`, часовой пояс `Europe/Chisinau`.

## 6. Миграция из PostgreSQL на EC2 (задание 9)

Исходная конфигурация приложения:

| Параметр | На EC2 до миграции | После миграции в RDS |
|---|---|---|
| Host | `db.timecapsule.internal` | `db.timecapsule.internal` (через CNAME) |
| PostgreSQL database | `mood_diary` | `mooddiary` |
| User | `mood_diary` (при экспорте) | `mooddiary` |
| Port | 5432 | 5432 |
| Движок | PostgreSQL 16 на EC2 | PostgreSQL 16 в RDS |

Во время диагностики выяснилось, что на старом сервере исходный пользователь называется `mood_diary`, а не `mooddiary`. После использования правильного имени удалось создать дамп.

### 6.1. Экспорт с app-server

```bash
umask 077
pg_dump -h db.timecapsule.internal -p 5432 -U mood_diary -d mood_diary --no-owner --no-privileges -f ~/mooddiary-lab5.sql
```

Флаги `--no-owner` и `--no-privileges` позволяют восстановить таблицы с владельцем нового пользователя без переноса старых ролей и GRANT.

### 6.2. Импорт в RDS

```bash
psql "host=RDS_ENDPOINT port=5432 dbname=mooddiary user=mooddiary sslmode=require" -X -v ON_ERROR_STOP=1 --single-transaction -f ~/mooddiary-lab5.sql
```

`RDS_ENDPOINT` в примере — адрес экземпляра из AWS Console. Команда успешно завершила восстановление схемы и данных.

## 7. Переключение приложения на RDS (задание 10)

В приватной Route 53 Hosted Zone `timecapsule.internal` прежняя запись `A`, направленная на EC2 `10.0.10.12`, заменена на `CNAME` с endpoint Amazon RDS. Благодаря этому адрес `DB_HOST=db.timecapsule.internal` в приложении сохранился.

Проверка вернула доменное имя RDS и успешное подключение к базе `mooddiary`. В SQL-сессии зафиксирован TLS 1.3 и приватный IP RDS `10.0.20.225`.

## 9. Архитектурное решение (задание 12)

Выбрана **RDS for PostgreSQL Single-AZ**: AWS управляет инфраструктурой СУБД и резервным копированием, а приложение сохраняет привычный интерфейс PostgreSQL. Настройка остаётся учебной: выделен один экземпляр без автоматического failover между AZ, поэтому отказ `eu-central-1a` приведёт к недоступности БД.

В [ADR-0004](docs/adr/0004-database-hosting.md) сопоставлены PostgreSQL на EC2, RDS Single-AZ, RDS Multi-AZ и Aurora PostgreSQL-Compatible, а также обсуждаются стоимость, ограничение резервного копирования, DNS и последствия отказа AZ.

Методичка оценивает работу базы `db.t4g.micro` с 20 GiB `gp3` при ~3 часах в день в течение трёх месяцев примерно в **$13–14**. Это ориентир из задания, не подтверждённый фактический счёт. Хранилище тарифицируется даже для остановленного RDS. После семи дней остановки сервис автоматически запускает экземпляр, поэтому расписание его периодической остановки полезно, но требуется контроль исполнения и AWS Billing.

## 10. Ответы на контрольные вопросы

**1. Почему для Security Group лучше указывать источник SG, а не IP?**  
Адрес EC2 может измениться при пересоздании или изменении сети. Ссылка на SG ограничивает доступ экземплярами, к которым она применяется, без необходимости поддерживать список IP вручную.

**2. Зачем две приватные подсети, если RDS работает в одной AZ?**  
DB Subnet Group должна обеспечивать покрытие разных AZ в регионе. Однако это не делает экземпляр Single-AZ отказоустойчивым — автоматическое переключение возможно только при соответствующей конфигурации Multi-AZ.

**3. Чем Read Replica отличается от Multi-AZ?**  
Read Replica используется преимущественно для разгрузки запросов чтения и получает изменения асинхронно. Multi-AZ обеспечивает резервирование основного экземпляра и механизм автоматического failover; реплика для чтения сама по себе не заменяет резервное копирование.

**4. Почему репликация не заменяет backup?**  
Удаление или ошибочное изменение данных обычно реплицируется вместе с правильными изменениями. Резервная копия и журналы транзакций позволяют восстановить состояние на выбранный поддерживаемый момент, если он доступен в окне хранения.

**5. Почему отдельный пользователь `mooddiary` лучше `dbadmin`?**  
PHP-приложению не нужны полномочия администратора всей RDS. Отдельная роль ограничивает последствия ошибки или компрометации приложения и упрощает разграничение прав.

**6. Почему после миграции не изменился `DB_HOST`?**  
Приложение обращается по частному DNS-имени `db.timecapsule.internal`. В Route 53 значение A было заменено на CNAME к endpoint RDS, а само логическое имя хоста осталось неизменным.

**7. Какие обязанности перешли к AWS после миграции?**  
AWS управляет инфраструктурой экземпляра RDS, автоматическими резервными копиями и регламентом обслуживания платформы. Разработчик по-прежнему отвечает за схему, данные, доступ приложения, конфигурацию, мониторинг расходов и проверку восстановления.

**8. Что происходит с `/health` при недоступной БД?**  
В MoodDiary проверка делает `SELECT 1`. При ошибке PDO возвращается HTTP 500 с `db:error`, а при успешном соединении — HTTP 200 с `db:ok`; дополнительный тест во время reboot RDS не проводился.

**9. Меняется ли endpoint RDS после Stop/Start?**  
DNS-имя endpoint обычно остаётся тем же; его IP-адрес может измениться. Поэтому приложению следует использовать DNS-имя, а не жёстко закреплённый IP RDS.

**10. Что случится при отказе `eu-central-1a`?**  
Поскольку выбран Single-AZ, приложение потеряет доступ к БД, пока сервис не восстановится или не будет выполнено восстановление/миграция на доступную инфраструктуру. Для автоматического failover следует применять Multi-AZ, что увеличивает расходы.

**11. Зачем EventBridge отдельная роль?**  
Scheduler исполняет действие AWS API от имени своей IAM-роли, а не от лица пользователя, который настроил расписание. Разрешение `rds:StopDBInstance` целесообразно ограничить ARN единственного экземпляра, чтобы расписание не могло останавливать другие БД.

**12. Что даёт retention = 1 day и сколько данных можно потерять?**  
Окно PITR ограничено одним днём истории, а не гарантирует нулевую потерю данных: доступная последняя точка восстановления может отставать от текущего момента. Восстановление до точки во времени создаёт новый экземпляр и потребует переключения приложения.

**13. Что происходит после семи дней остановки RDS?**  
AWS автоматически запускает остановленный экземпляр для обслуживания. Поэтому отключение на ночь требует работающего расписания и периодической проверки состояния, иначе вычислительные ресурсы могут снова тарифицироваться.

**14. Как запрос проходит от браузера до базы?**  
Браузер обращается к Nginx на EC2, запрос обрабатывает PHP-FPM, а PHP использует PDO PostgreSQL. DNS в приватной Route 53 разрешает `db.timecapsule.internal` в endpoint RDS; SG допускает TCP 5432 только от группы приложения, затем PostgreSQL проверяет TLS/учётные данные и SQL-права.

## 11. Вывод

В лабораторной выполнена основная продвинутая задача: база MoodDiary перенесена с самостоятельно обслуживаемого PostgreSQL на EC2 в приватный Amazon RDS. Данные успешно выгружены и восстановлены, таблицы и количество записей совпадают, приложение подключено по прежнему DNS-имени и продолжило работать после остановки старого сервера. Управляемый сервис упрощает эксплуатацию, но при выбранном Single-AZ и однодневном backup retention сохраняются ограничения по доступности и глубине восстановления.

Дополнительные учебные задачи Read Replica/PITR и часть тестов обслуживания были сознательно сокращены. Фактическое исполнение Scheduler и завершение очистки старой инфраструктуры остаются отдельными контрольными действиями.
