# 2. Подготовка приложения к развёртыванию

До переноса приложения в AWS были исправлены проблемы, которые могли проявиться при запуске под Linux.

### 2.1. Исправление подключения к базе данных

Из `src/Core/Database.php` были удалены обращения к несуществующей глобальной переменной `$pdo`. Настройки PDO теперь задаются при создании соединения внутри `Database::getConnection()`.

### 2.2. Исправление регистра имён файлов

Windows обычно использует файловую систему без учёта регистра, а Linux различает имена файлов по регистру. Поэтому в `public/index.php` были исправлены пути:

```php
require_once __DIR__ . '/../src/Core/CSRF.php';
require_once __DIR__ . '/../src/Helpers.php';
```

### 2.3. Исправление системы миграций

Изначально несколько миграций объявляли одинаковые глобальные функции `up()` и `down()`, что приводило бы к повторному объявлению функций. Миграции были переведены на формат, в котором каждый файл возвращает массив с замыканиями `up` и `down`, а `migrate.php` последовательно применяет ещё не выполненные миграции.

Локальная проверка после исправления:

```text
Пропущена: 001_create_mood_diary_tables.php
Пропущена: 002_add_users_and_auth.php
Миграции успешно применены.
```

### 2.4. Вынос параметров БД в `.env`

Пароль и параметры PostgreSQL были удалены из `config.php`. Локальные и серверные настройки теперь хранятся в `.env`, который исключён из Git.

Пример `.env.example`:

```ini
DB_HOST=localhost
DB_PORT=5432
DB_NAME=mooddiary
DB_USER=mooddiary
DB_PASSWORD=change_me
DB_CHARSET=utf8
```

В `.gitignore` добавлены:

```gitignore
/.env
/vendor/

/.idea/
/.vscode/

*.log
```

Это позволяет хранить исходный код в публичном репозитории без публикации пароля БД и без добавления Composer-зависимостей в Git.

### Ответ на вопрос: что разрешает AdministratorAccess и почему нельзя постоянно использовать root?

`AdministratorAccess` предоставляет пользователю IAM полный доступ к ресурсам и операциям AWS, но пользователь остаётся отдельной управляемой учётной записью. Root-аккаунт имеет максимальные полномочия, включая критические операции с самим аккаунтом, поэтому его постоянное использование увеличивает последствия компрометации учётных данных. Для повседневной работы безопаснее использовать IAM-пользователей и выдавать им только необходимые права.

## 4.5. Настройка PHP-FPM и nginx

PHP-FPM был включён и запущен:

```bash
sudo systemctl enable --now php-fpm
```

Проверено наличие Unix-сокета:

```bash
ls -l /run/php-fpm/www.sock
```

Для nginx создан виртуальный хост `/etc/nginx/conf.d/mood-diary.conf`:

```nginx
server {
    listen 80 default_server;
    listen [::]:80 default_server;

    root /var/www/mood-diary/public;
    index index.php;

    location = /health {
        include fastcgi_params;
        fastcgi_pass unix:/run/php-fpm/www.sock;
        fastcgi_param SCRIPT_FILENAME $document_root/health.php;
    }

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        try_files $uri =404;
        include fastcgi_params;
        fastcgi_pass unix:/run/php-fpm/www.sock;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    }

    location ~ /\. {
        deny all;
    }
}
```

# 5. Обновление приложения через deploy.sh

Для воспроизводимого обновления приложения создан скрипт `~/deploy.sh`:

```bash
#!/bin/bash
set -euo pipefail

cd /var/www/mood-diary

echo "==> Забираем новый код из GitHub"
git pull --ff-only

echo "==> Устанавливаем зависимости"
composer install --no-dev --optimize-autoloader --no-interaction

echo "==> Применяем миграции"
php migrate.php

echo "==> Перезагружаем PHP-FPM"
sudo systemctl reload php-fpm

echo "Готово. На сервере коммит: $(git log -1 --oneline)"
```

Скрипт сделан исполняемым:

```bash
chmod +x ~/deploy.sh
```

После проверки на сервере деплой был запущен непосредственно с локального Windows-компьютера:

```powershell
ssh -i $HOME\.ssh\neural-emerald-aws-key.pem ec2-user@<Public-IP> ./deploy.sh
```

![Запуск deploy.sh через SSH](images/deploy.png)

Таким образом, типичный выпуск новой версии выполняется по цепочке:

```text
Локальный компьютер
       |
       | git push
       v
     GitHub
       |
       | git pull --ff-only
       v
      EC2
       |
       +--> composer install
       +--> php migrate.php
       +--> reload PHP-FPM
```

### Что может произойти во время `git pull`?

Рабочие файлы приложения обновляются непосредственно в каталоге, из которого nginx обслуживает запросы. Пользователь, попавший на сайт в этот момент, теоретически может получить состояние, в котором часть файлов уже относится к новой версии, а часть ещё нет. Если после обновления кода не выполнить `composer install`, новая версия может ожидать зависимости, которых ещё нет в `vendor/`, что приведёт к ошибке приложения.

Endpoint `/health` выполняется отдельным PHP-файлом и проверяет, что PHP работает и соединение с PostgreSQL доступно. Ошибка в Twig-шаблоне главной страницы не затрагивает этот путь. Такой health-check неполон: он не проверяет рендеринг пользовательских страниц, работоспособность всех маршрутов и корректность бизнес-логики.

### Сколько времени сайт был недоступен и как уменьшить это время?

Точное время недоступности во время эксперимента отдельно не фиксировалось. Оно состояло из времени обнаружения ошибки, создания и отправки revert-коммита и повторного запуска `deploy.sh`. Сократить его можно автоматическими тестами до деплоя, CI/CD, проверкой health-check после развёртывания, автоматическим rollback и атомарной схемой релизов, при которой рабочая версия переключается только после полной подготовки новой.

# 8. Ответы на контрольные вопросы продвинутого уровня

## 8.1. Как запрос проходит от браузера до базы данных?

Браузер отправляет HTTP-запрос на публичный IP EC2, где порт 80 обслуживает nginx. Для статических файлов nginx может вернуть содержимое самостоятельно; PHP-запрос он передаёт PHP-FPM через Unix-сокет `/run/php-fpm/www.sock`. PHP-код приложения при необходимости использует PDO и отправляет SQL-запросы PostgreSQL, который работает на том же экземпляре и доступен только локально на порту 5432.

## 8.2. Почему сервер может скачивать код, но не может отправлять изменения в GitHub?

Репозиторий публичный, поэтому чтение кода по HTTPS не требует аутентификации. Для `git push` необходимо предоставить GitHub учётные данные или специальный ключ с правом записи; серверу такие права не выдавались. Это безопаснее, потому что компрометация EC2 не должна автоматически давать злоумышленнику возможность изменить исходный репозиторий.

## 8.3. Что произойдёт с файлами при удалении экземпляра EC2?

При обычном `Stop` содержимое EBS-тома сохраняется, поэтому после повторного `Start` файлы, конфигурация и PostgreSQL остаются на месте. При `Terminate` корневой EBS-том обычно настроен на удаление вместе с экземпляром; в таком случае локально сохранённые файлы и база данных будут потеряны. Поэтому важные данные в реальной архитектуре необходимо хранить с учётом резервного копирования и политики жизненного цикла EBS.

## 8.4. Что общего у deploy.sh с CI/CD и чего ещё не хватает?

`deploy.sh` автоматически выполняет повторяемую последовательность доставки новой версии: получает код, устанавливает зависимости, применяет миграции и перезагружает PHP-FPM. Это напоминает deployment-стадию CI/CD. В текущем варианте отсутствуют автоматический запуск по событию в Git, сборка и тестирование, отдельное окружение, проверка результата деплоя, стратегия zero-downtime и автоматический rollback.

# 9. Дополнительные ответы на вопросы по работе

### Чем Stop отличается от Terminate и за что платят при остановленном экземпляре?

`Stop` выключает вычислительный экземпляр, но сохраняет его EBS-тома и конфигурацию. `Terminate` удаляет экземпляр; корневой EBS при стандартной настройке также удаляется. При остановленном EC2 не начисляется плата за вычислительное время экземпляра, однако сохраняемые EBS-тома продолжают занимать оплачиваемое хранилище.

### Почему PostgreSQL использует отдельного пользователя приложения?

Приложение не должно работать от имени административного пользователя PostgreSQL. Пользователь `mooddiary` владеет своей базой и используется только приложением, что уменьшает область возможного ущерба при компрометации его учётных данных.

### Почему база не открыта через Security Group?

PostgreSQL находится на том же EC2, что и приложение, и PHP подключается к `localhost:5432`. Открывать порт 5432 в интернет для данной архитектуры не требуется и небезопасно.
