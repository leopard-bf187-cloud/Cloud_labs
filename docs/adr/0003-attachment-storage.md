# ADR-0003. Хранение пользовательских вложений в Amazon S3

- **Статус:** принято
- **Дата:** 2026-10-28
- **Приложение:** Mood Diary (PHP, Twig, PostgreSQL)
- **Регион:** AWS eu-central-1 (Frankfurt)
- **Связанные работы:** Cloud Computing, ЛР3 → ЛР4

## Контекст

После ЛР3 приложение Mood Diary работало на EC2 `app-server` через Nginx и PHP-FPM, а PostgreSQL находился на отдельном `db-server` в приватной подсети. Административный SSH-доступ проходил через `bastion`.

ЛР4 требует переместить содержимое загружаемых файлов в объектное хранилище, чтобы файлы не зависели от локального диска конкретной EC2-инстанции. Исходная версия Mood Diary не поддерживала вложения, поэтому существующие локальные пользовательские файлы мигрировать было неоткуда. Функция вложений реализована непосредственно в рамках ЛР4: PNG, JPEG и PDF размером до 10 МиБ.

## Рассмотренные варианты

| Критерий | Amazon EBS | Amazon EFS | Amazon S3 |
|---|---|---|---|
| Тип | Блочное хранилище, подключаемое к EC2 | Управляемая общая файловая система NFS | Объектное хранилище |
| Доступ из PHP | Локальный путь в файловой системе | Путь через NFS-монтирование | API через AWS SDK |
| Совместный доступ | Обычно для одного сервера/AZ; Multi-Attach ограничен | Несколько EC2 могут работать с общей файловой системой | Любое разрешённое приложение обращается к объектам по API |
| Масштабирование | Нужно управлять томами и их подключением | Нужно настроить сеть и точки монтирования | Новым серверам достаточно IAM-доступа и конфигурации |
| Управление версиями | Дополнительные средства/снимки EBS | Дополнительные средства резервирования | S3 Versioning и Lifecycle |
| Доступ к одному файлу из браузера | Обычно через веб-приложение | Обычно через веб-приложение | Временная подписанная ссылка на GetObject |
| Затраты | Выделенная ёмкость и характеристики тома | Используемое пространство и режим хранения/доступа | Занятый объём, API-запросы, классы хранения, трафик |
| Недостатки | Зависимость от управления томом и сервером | NFS, стоимость и сетевая конфигурация | Отсутствие POSIX-интерфейса; обращения по API |

В этой учебной работе численные тарифы не сравнивались, поскольку стоимость зависит от фактической нагрузки и региона.

## Решение

Выбрано **Amazon S3**. Содержимое файлов помещается в приватный бакет `timecapsule-dev-uploads-leopard`, ключи создаются под префиксом `uploads/`. В PostgreSQL хранится только метаинформация в таблице `entry_attachments`: ссылка на запись дневника, ключ S3, оригинальное имя, MIME-тип, размер файла и дата создания.

Приложение использует AWS SDK for PHP и **EC2 Instance Profile** с IAM Role `timecapsule-dev-app-role`. Постоянные ключи доступа в исходном коде и `.env` не используются. Политика `timecapsule-dev-app-s3` разрешает только `s3:GetObject`, `s3:PutObject` и `s3:DeleteObject` для `arn:aws:s3:::timecapsule-dev-uploads-leopard/uploads/*`. Разрешение `s3:ListBucket` удалено после миграционного этапа.

Бакет приватный (Block Public Access), с SSE-S3, Versioning, Lifecycle для устаревших версий и bucket policy, запрещающей обращения без HTTPS.

## Потоки данных

### Загрузка

1. Авторизованный пользователь прикладывает PNG, JPEG или PDF при создании/редактировании записи.
2. PHP проверяет ошибку загрузки, MIME-тип и размер до 10 МиБ.
3. `AttachmentStorage` загружает содержимое в S3 с помощью `PutObject`.
4. `AttachmentRepository` записывает метаданные в PostgreSQL. Если запись в БД не удалось сохранить, приложение пытается удалить созданный объект.

**Сервер не хранит вложения в постоянной локальной папке.** Временный PHP upload-файл на время обработки HTTP-запроса возможен, но не является постоянным хранилищем.

### Скачивание

1. Пользователь открывает ссылку на вложение внутри Mood Diary.
2. PHP проверяет сессию и право пользователя на связанную запись дневника.
3. Приложение генерирует **Presigned GET URL сроком на 300 секунд (5 минут)** и возвращает HTTP 302.
4. Браузер скачивает объект непосредственно из S3, не передавая файл через PHP-сервер.

Время жизни ссылки ограничивается параметром SigV4 `X-Amz-Expires=300`, а также действительностью временных AWS credentials, которыми она подписана. Любой, кто получил действующую ссылку, может использовать её до истечения срока; поэтому полный URL нельзя включать в общедоступный отчёт.

### Удаление

Приложение вызывает `DeleteObject` и удаляет метаданные. При включённом Versioning обычное удаление добавляет Delete Marker; предыдущая версия объекта может сохраняться. Полное удаление версий приложению не разрешено.

## Последствия

### Пользовательский доступ и безопасность

Приватные объекты не доступны по постоянным публичным URL. Сначала требуется авторизация в Mood Diary, затем браузер получает краткосрочный подписанный URL. Для IAM Role ограничен доступ к другим префиксам, в частности к `backups/`.

### Защита данных и контроль стоимости

**Versioning** позволяет восстановить предыдущие версии объектов при случайном удалении или перезаписи, если версия ещё не удалена. Настроенное **Lifecycle Rule** переводит noncurrent-версии под `uploads/` в Standard-IA спустя 30 суток и удаляет устаревшие версии по правилам с истечением в 90 суток (с сохранением до двух более новых noncurrent-версий). Незавершённые multipart uploads удаляются спустя 7 суток. Это ограничивает накопление устаревших файлов, но не исключает затраты на хранилище, запросы и трафик.

### Масштабирование до нескольких серверов приложения

Если перед двумя или более экземплярами `app-server` появится **Application Load Balancer**, содержимое вложений переносить не потребуется: все серверы смогут обращаться к одному S3-бакету через собственные IAM Instance Profiles. PostgreSQL продолжит хранить общие метаданные.

Для действительно stateless-масштабирования понадобится отдельно решить хранение PHP-сессий (например, вынести их из локальных файлов в общее хранилище), синхронизацию версий приложения, конфигурации, health checks и сетевой доступ. ALB и несколько серверов здесь описаны как **возможное дальнейшее развитие**, а не как уже развёрнутая инфраструктура.

### Компромиссы и риски

- При недоступности S3 операции с файлами становятся недоступными, даже если сам сайт и PostgreSQL работают.
- Операции между S3 и PostgreSQL не образуют единой транзакции: в случае частичной ошибки возможны «осиротевшие» объекты или метаданные; нужны компенсирующие операции и потенциальная периодическая сверка.
- Версионирование не равно полноценной политике резервного копирования: удаление старых версий через Lifecycle может быть необратимым.
- Нужно учитывать стоимость API-запросов, хранения предыдущих версий и интернет-трафика.

## Подтверждение в лабораторной работе

- `aws sts get-caller-identity` на EC2 подтвердил `assumed-role/timecapsule-dev-app-role`.
- `storage/uploads` на сервере отсутствует, при этом загрузка изображения в S3 через Mood Diary была успешной.
- IAM Role получила `AccessDenied` при попытке просмотреть `backups/`.
- `HeadObject` несуществующего файла первоначально вернул 404, а после удаления `s3:ListBucket` — 403.

Отдельные действия (восстановление удалённой версии, тест PDF, доступ другого пользователя) следует отмечать как проверенные только при наличии соответствующего результата.
