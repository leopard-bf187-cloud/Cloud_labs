# ADR-0004. Размещение PostgreSQL приложения MoodDiary

- **Статус:** принято для учебной среды (часть проверок не проводилась)
- **Дата:** 2026-11-16
- **Регион:** `eu-central-1` (Frankfurt)
- **Приложение:** [MoodDiary](https://github.com/leopard-bf187-cloud/LaboratoryApp) (PHP, Nginx, PostgreSQL, Amazon S3)
- **Связанная работа:** Cloud Computing, ЛР5 (миграция с EC2 на Amazon RDS)

## Контекст

В ЛР3–ЛР4 MoodDiary работал на EC2 `app-server` (`10.0.0.213`), а PostgreSQL 16 — на отдельном EC2 `db-server` (`10.0.10.12`). Исходная база называлась `mood_diary`. Приватная запись Route 53 `db.timecapsule.internal` ссылалась на IP старого сервера. Метаданные вложений размещались в PostgreSQL, сами файлы — в приватном S3 `timecapsule-dev-uploads-leopard`.

Требуется перенести PostgreSQL в управляемый сервис, не делая БД публичной, сохранить работоспособность PHP-приложения и ограничить расход облачных ресурсов.

## Рассмотренные варианты

| Вариант | Управление и резервное копирование | Доступность | Расходы и ограничения |
|---|---|---|---|
| PostgreSQL на EC2 | ОС, PostgreSQL, обновления и резервирование на стороне разработчика | Зависит от собственной схемы отказоустойчивости | Оплачивается EC2/EBS; больше ручной работы |
| RDS PostgreSQL Single-AZ | AWS управляет инфраструктурой и предоставляет автоматическое резервное копирование | Отказ выбранной AZ приводит к недоступности экземпляра | Подходит для учебной среды, нет автоматического переключения между AZ |
| RDS PostgreSQL Multi-AZ | Управляемая синхронная резервная инфраструктура и автоматическое переключение | Более высокая доступность при отказе AZ | Дороже Single-AZ |
| Amazon Aurora PostgreSQL-Compatible | Управляемый кластер, распределённое хранилище и варианты реплик/отказоустойчивости | Конфигурация зависит от выбранной архитектуры кластера | Избыточен для учебного MoodDiary и потенциально дороже |

## Решение

Использовать **Amazon RDS for PostgreSQL 16, Single-AZ**, идентификатор `mooddiary-dev-rds`, с приватным сетевым доступом из `app-server` по TCP 5432. Параметры, выбранные при создании: `db.t4g.micro`, 20 GiB `gp3`, без Storage Autoscaling и Multi-AZ; публичный доступ отключён. Создана `mooddiary-dev-db-subnets` на двух подсетях из `eu-central-1a` и `eu-central-1b`, а Security Group `mooddiary-dev-rds-sg` ограничивает входящий доступ группой приложения.

В PostgreSQL создана база `mooddiary` с владельцем `mooddiary`; для администрирования остаётся `dbadmin`. Исходная `mood_diary` экспортирована через `pg_dump --no-owner --no-privileges`, импортирована в RDS и проверена по таблицам `users`, `entries`, `moods`, `entry_attachments`. В Route 53 запись `db.timecapsule.internal` заменена с A на CNAME, направленный на endpoint RDS. В приложении обновлены название базы и пароль, а `DB_HOST` сохранён прежним.

Для ограничения затрат создано расписание EventBridge Scheduler `mooddiary-dev-rds-nightly-stop` с ролью `mooddiary-dev-scheduler-role` и разрешением `rds:StopDBInstance` для одной БД. На скриншоте настройки виден **cron `30 23 * * ? *`** с зоной `Europe/Chisinau`; целевой вариант на архитектурной схеме — `0 23 * * ? *`. Запуск расписания не проверялся. До использования для контроля бюджета требуется сверить фактический cron и ARN ресурса в прикреплённой IAM-политике.

## Последствия

### Резервное копирование и RPO/RTO

По ограничениям аккаунта AWS Free Plan вместо требуемых методичкой семи дней установлено **backup retention = 1 day**. RDS создаёт автоматические резервные копии и сохраняет журналы транзакций, необходимые для восстановления на доступный момент (PITR), однако при очень свежих изменениях существует отставание `Latest restore time`. Однодневное окно **не означает** допустимую потерю данных ровно за сутки: оно ограничивает глубину возврата, а фактическая потеря при аварии определяется последней доступной точкой восстановления. Восстановление создаёт отдельный экземпляр, поэтому потребуется время на создание и переключение DNS. В ЛР5 восстановление из резервной копии практически не проверялось.

### Стоимость

При работе RDS оплачиваются вычисления и хранилище; выделенное хранилище сохраняет стоимость и после остановки экземпляра. Методичка ориентировочно оценивает три месяца использования `db.t4g.micro` и 20 GiB `gp3` при работе около 3 часов в день в **$13–14** (оценка, не фактический счёт). RDS автоматически запускается после семи дней остановки; созданный Scheduler предназначен для ежедневного выключения, однако успешные выполнения ещё не подтверждены. За расходами необходимо следить в AWS Billing.

### Сетевые пути и безопасность

Маршрут из PHP: `DB_HOST=db.timecapsule.internal` → private Route 53 CNAME → RDS endpoint → приватный IP RDS в VPC → TCP 5432. Пользователь `mooddiary` не использует административную учётную запись `dbadmin`. SQL-проверка `psql` подтвердила TLS 1.3; конфигурация проверки серверного сертификата в PHP отдельно не аудировалась. Секреты и дамп, содержащий хеши паролей, нельзя публиковать в Git.

### Отказ зоны доступности

Рабочий RDS находится в **одной** AZ, хотя DB Subnet Group охватывает две. При отказе `eu-central-1a` приложение потеряет доступ к БД; наличия второй подсети **недостаточно** для автоматического failover. Для рабочего сервиса с требованиями высокой доступности следует рассмотреть RDS Multi-AZ, увеличить срок хранения backup, установить мониторинг и протестировать план восстановления.

### Границы проведённых проверок

Фактически подтверждены успешный импорт, совпадение количества строк, разрешение CNAME, соединение PHP с RDS и работа сайта после отключения старого `db-server`. Не выполнялись отдельная учебная read replica, PITR, тест Scheduler, перезагрузка/остановка RDS с наблюдением `/health`, проверка CloudTrail.
